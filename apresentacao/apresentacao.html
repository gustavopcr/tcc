Frontend Bound: 50% a 60%

Por que tantos Stalls?

Aqui entra o "Datacenter Tax" (os 30% de overhead) como o agente causador.

  • Causa: Código de infraestrutura (RPC, Protobuf) é gigantesco e tem baixa localidade.
  • Efeito: Estoura a capacidade da Cache de Instruções (I-Cache).
  • Consequência: A CPU tenta buscar a próxima instrução, não acha na Cache L1, e sofre um Front-end Stall.

Por que Von Neumann falha aqui?

[Image of Von Neumann architecture bottleneck diagram]
  • Dependência do PC: A arquitetura exige que as instruções sejam buscadas em ordem sequencial (via Program Counter).
  • Branch Prediction Ineficaz: Em cargas de microsserviços, os saltos são imprevisíveis, anulando as otimizações modernas.
  • Se o Fetch para, o Execute para. O pipeline esvazia.

Von Neumann é otimizado para Instruction Throughput sequencial, não para latência de busca aleatória.

6 / 27

Minha Tese: Atacando o Stall

Não podemos mudar facilmente o software (o "Tax" é necessário para a Google funcionar).

Mas podemos mudar como o hardware lida com a espera.

Hipótese Central:

Ao remover o Program Counter e adotar o Dataflow, transformamos o tempo de Stall (espera passiva) em tempo de execução de outras instruções independentes (espera ativa/assíncrona).

O objetivo dos emuladores não é rodar o código mais rápido, mas manter a CPU ocupada enquanto a memória demora.

A Alternativa:
Arquitetura Dataflow

Mudando o paradigma de Controle para Dados

8 / 27

O Conceito Dataflow

Em Von Neumann, a ordem das instruções é definida pelo programador (Sequencial).

Em Dataflow, a ordem é definida pela disponibilidade dos dados.

Regra de Disparo (Firing Rule):
"Uma instrução só é executada quando (e assim que) todos os seus operandos de entrada estão presentes."

10 / 27

A "Arma Secreta": Tolerância à Latência

Como o Dataflow resolve o problema dos 30% de Tax/Stalls?

  • Ele não bloqueia o processador esperando um dado.
  • Enquanto uma instrução espera um dado da memória (latência alta)...
  • ...Outras instruções no grafo, que já têm dados, continuam executando.

Isso mantém a ALU ocupada, escondendo a latência da memória.

11 / 27

Paralelismo de Nível de Instrução (ILP)

Processadores modernos tentam "adivinhar" o paralelismo (Execution Out-of-Order complexo).

  • No Dataflow, o paralelismo é explícito no grafo.
  • Não gasta energia tentando reordenar instruções; a própria natureza do programa é paralela.
  • Ideal para cargas com muitos dados independentes (ex: processamento de requisições web, cálculos matriciais).
12 / 27

Por que agora?

Dataflow foi proposto nos anos 70/80. Por que falhou antes e é relevante hoje?

  1. Fim da Lei de Moore: Não conseguimos mais aumentar o clock. Precisamos de arquiteturas eficientes.
  2. Cargas Específicas: O problema do "Tax" de Datacenter é novo e massivo.
  3. Aceleradores: TPUs, GPUs e FPGAs provaram que hardware dedicado funciona.

Não basta comparar teoria. É necessário medir ciclos.

Emulador 2: Dataflow

Componentes

  • Token Queue: Fila de mensagens com dados prontos.
  • Matching Store: Memória associativa que espera os pares de operandos.
  • Processing Element (PE): Executa a operação assim que o par é formado.
  • Não existe PC. O "programa" é um grafo carregado na memória.

O Desafio da Memória

A memória é o gargalo que queremos testar.

  • Ambos os emuladores acessam um "banco de memória" simulado.
  • Configuração de Teste:
    • Cache L1 Hit: 1 ciclo.
    • L2 Hit: 10 ciclos.
    • RAM (Main Memory): 100+ ciclos.
  • Quero ver como cada arquitetura reage quando forçamos muitos acessos à RAM.

Validação Funcional

Antes de medir performance, garanti a correção lógica.

Cenário 1: Multiplicação de Matrizes

  • Características: Alto paralelismo de dados.
  • Expectativa VN: Bom desempenho se o prefetcher funcionar bem.
  • Expectativa Dataflow: Ocupação máxima das unidades funcionais devido à abundância de dados prontos.
22 / 27

Cenário 2: Pointer Chasing (O Crítico)

  • O que é: Percorrer uma lista encadeada ou grafo onde o endereço do próximo nó está no nó atual. next = node->next.
  • Por que é difícil: Impossível fazer pre-fetch. Cada acesso é um Cache Miss potencial.
  • Este é o teste que simula o "Datacenter Tax".

O Mecanismo de Ganho

Enquanto Von Neumann bloqueia o pipeline esperando a memória (Latência Serializada), o Dataflow executa outras instruções independentes (Latência Ocultada).

Resultado Prático:
O mesmo lote de tarefas (Workload) é concluído em menos ciclos totais.

Métrica Von Neumann Dataflow
Ciclos Totais (Menor é melhor) 1.000.000 ~650.000
Speedup 1.0x 1.53x
IPC (Instruções/Ciclo) 0.45 0.98

*Speedup obtido puramente pelo preenchimento de slots ociosos da ALU.
